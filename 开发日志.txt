飞书成员账号开通/回收机器人 —— 开发日志

--------------------------------------------------
一、项目背景与目标
--------------------------------------------------
1. 需求：用飞书机器人完成“人员账号的开通与回收”。
2. 澄清后的目标（与用户确认）：
   - 操作对象 = 飞书通讯录成员本身（contact/v3 API），不涉及内网系统；
   - 回收默认“停用”（冻结，可恢复），同时支持“彻底删除（离职）”；
   - 执行模式 = 默认直连执行，可选卡片审批（删除默认审批）；
   - 技术栈 = Python + FastAPI（本地/服务器运行）；
   - 应用凭证已由用户提供（开发者后台自建应用）。
3. 交付形态：可直接部署的 Web 服务，/webhook 接收飞书回调，/healthz 健康检查。

--------------------------------------------------
二、方案与架构
--------------------------------------------------
1. 指令模型（私聊，或群聊 @机器人）：
   开通 姓名 手机号 [邮箱] [部门=od-xxx] [工号=xxx] [职务=xxx] [英文名=xxx]
   停用/冻结/回收 <手机号|邮箱|open_id>          （is_frozen=true，可恢复）
   启用/解冻 <手机号|邮箱|open_id>               （is_frozen=false）
   删除/彻底删除 <手机号|邮箱|open_id> [备注]     （离职，默认审批）
   查询/查 <手机号|邮箱|open_id>
   帮助 / 我的ID / 日志 [条数]
2. 关键 API（已按官方文档核实）：
   - 创建成员：POST /contact/v3/users（需 name/mobile/department_ids，发加入邀请）
   - 停用/启用：PATCH /contact/v3/users/:id 的 is_frozen 字段（限 1 QPS）
   - 删除（离职）：DELETE /contact/v3/users/:id（资源可转交）
   - 恢复离职成员：POST /directory/v1/employees/:employee_id/resurrect（directory v1，
     需商业专业版+、离职 30 天内；权限 directory:employee.resurrect:write）
   - 身份解析：POST /contact/v3/users/batch_get_id（手机号/邮箱→open_id）
   - 消息收发：POST /im/v1/messages；事件 im.message.receive_v1
3. 代码分层（app/）：
   config.py      .env 配置加载
   feishu_client.py  tenant_access_token 缓存 + 通讯录/消息封装 + 错误码中文化
   parser.py      中文指令解析（别名、手机号规范化、客套语）
   lifecycle.py   身份解析、查重、开通/冻结/解冻/删除、1QPS 限速
   actions.py     统一动作执行器 + 审计摘要（手机号脱敏）
   approval.py    审批状态机（CAS 防重复决策）
   storage.py     审批单 + 审计日志本地持久化（JSON/JSONL）
   messages.py    文本与卡片构造
   crypto_utils.py Encrypt Key AES-256-CBC 加解密（含单测）
   server.py      FastAPI：/webhook（事件+卡片回调同址兼容）、/healthz
   cli.py         运维工具：check / departments / whoami
4. 安全设计：
   - 操作员白名单 OPERATOR_OPEN_IDS（默认空 = 全拒绝，fail-closed）；
   - 删除默认强制审批；审批人白名单 APPROVER_OPEN_IDS；
   - 开通前按手机号/邮箱查重（含离职成员），client_token 幂等；
   - 审计日志全量落盘 data/audit.jsonl；回显手机号脱敏。

四、遇到的问题与解决方法
--------------------------------------------------
1.【环境】本机 pip/pytest 受沙箱权限限制（pip 无法写系统临时目录）。
   - 现象：pip 安装 pytest 反复失败；pytest 依赖 tmp_path 的用例报权限错。
   - 解决：临时目录/缓存改到工作区内；受限环境下以全权限模式运行测试套件。
   - 备注：属开发机环境特性，与交付代码无关；生产服务器正常 pip install 即可。

2.【编码】Config.is_approval 被误加 @property。
   - 现象：指令路由抛 TypeError: is_approval() missing 1 required positional argument。
   - 解决：移除 @property 恢复普通方法；新增 tests/test_config.py 回归用例。

3.【飞书规则】对“待加入(未接受邀请)”成员执行停用返回 44010。
   - 现象：停用刚开通、尚未接受邀请的成员 → unJoined user not allow to update。
   - 解决：执行前识别 is_unjoin，直接给出可操作建议（等接受邀请后停用，或改用删除）；
         错误码表补充 44010/44011 中文提示；新增回归测试。
   - 备注：这是飞书业务规则而非代码缺陷。

4.【联调】URL 验证“Challenge code 没有返回”（两次不同根因）。
   - 根因1：后台开启了 Encrypt Key，challenge 请求为加密包体，而 .env 未配
          FEISHU_ENCRYPT_KEY，服务返回 400。
   - 根因2：.env 的 FEISHU_VERIFICATION_TOKEN 与后台“加密策略”显示值不一致，
          请求被 403 拒绝。
   - 解决：按官方 FAQ 确认——加密仅影响请求体，服务需解密后原样回传 challenge；
         服务端增加可操作的中文日志；指导用户核对/复制后台值。
   - 最终选择“路线A”：后台关闭加密、.env 两个键留空，URL 验证一次通过。

5.【配置】审批卡片点击报“该应用尚未配置卡片回调”。
   - 原因：事件订阅请求地址 ≠ 卡片回调地址，二者在后台分开配置。
   - 解决：将同一 /webhook 地址填到“卡片回调/消息卡片请求网址”（保持不加密）；
         /webhook 自动区分事件与卡片两种请求体。

6.【字段权限】通讯录部门列表名称显示“(未命名)”。
   - 原因：缺少“获取部门基础信息(contact:department.base:readonly)”字段权限。
   - 解决（指引用户）：后台补权限并发布版本，重跑 python -m app.cli departments。

7.【限速】冻结/解冻(is_frozen)接口限制 1 QPS。
   - 解决：模块级全局锁 + 相邻调用间隔限速，串行化所有冻结类 PATCH。

8.【网络/隧道】从外部环境直连 cpolar 域名 TLS 断开。
   - 现象：本会话沙箱访问 https://*.cpolar.top 失败。
   - 定位：用户本机 curl 可达且服务正常返回 → 属隧道/访问方差异；
         结合日志(403/400)最终定位到配置(加密/Token)问题，而非隧道故障。

9.【设计取舍】飞书无“按姓名搜索用户”的租户凭证接口。
   - 决策：身份一律用 手机号/邮箱/open_id 定位；README 中说明获取姓名检索的替代思路。

10.【飞书规则/状态误判】离职(删除)后再“开通”同手机号，及“启用”已离职账号。
   - 现象1：删除成员(离职)后，用同手机号“开通”提示“已是在职成员，无需重复开通”——
          但飞书人事里该人明明是“已离职”。
   - 现象2：“启用”该账号返回 42006 user has resigned error。
   - 根因：离职成员的手机号/邮箱在租户内仍被占用（恢复/清理前不可用同号新建）；
          且应用未开通“获取用户受雇信息(contact:user.employee:readonly)”字段权限时，
          get_user/batch_get_id 不返回 is_resigned 等状态，机器人无法区分
          “在职/停用/离职/待加入”，误落到“在职”分支提示。
   - 解决：
         a) provision 冲突分支改为按状态精确提示（离职→指引管理后台“恢复”或释放手机号后重建；
            待加入→等待接受或先删除邀请；停用→先启用；状态不可读→明示缺字段权限并给人工核对路径），
            不再武断报“在职”；
         b) 错误码表新增 42006 中文提示；
         c) 新增 3 项单测：离职占用/待加入占用/状态不可读不得误报“在职”。
   - 正确业务语义：同一人回归 = 管理后台“恢复离职成员”（原账号直接可用），而非“重新开通”；
     全新账号需先释放手机号/邮箱。
   - 待办：若需机器人直连“恢复离职员工”，核实并接入飞书目录类恢复接口
     （directory-v1/employee/resurrect 类，视租户支持情况）。

11.【功能】新增“恢复（离职回归）”指令，接通“恢复离职员工”API。
   - 接口核实：POST /open-apis/directory/v1/employees/:employee_id/resurrect
     （employee_id_type=open_id；限频 10 次/分钟）。
   - 前置条件（来自官方文档）：企业版本需商业专业版及以上；员工需在离职 30 天内；
     其 ID/手机号/邮箱不能被其他成员占用；应用需开通
     “恢复离职员工(directory:employee.resurrect:write)”或
     “创建、更新、离职、恢复员工(directory:employee:write)”权限。
   - 指令：恢复 <手机号|邮箱|open_id>（别名：恢复账号/离职恢复/恢复离职/resurrect）。
   - 交互逻辑：非离职状态（能读到状态时）→ 提示无需恢复；离职或状态不可读 → 调用恢复接口，
     成功回显“已恢复为在职”，失败按错误码 2221xxx 给出中文原因（版本/权限/占用/流程中/席位等）。
   - 配置：新增 RESTORE_MODE（默认 direct）。
   - 权限使用说明：contact:user.employee:readonly（获取用户受雇信息）用于确认成员是否离职，
     是“恢复/停用/开通查重”等状态判断的基础，已在 README 与帮助文本中说明。
   - 测试：新增解析器(恢复别名)、动作层(离职可恢复/在职拦截/启用离职指向恢复)与配置(默认direct)用例。
